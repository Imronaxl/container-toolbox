# hello-app

Веб-сервис «Hello World» на Python/Flask, упакованный в Docker и развёрнутый в локальном Kubernetes через Minikube. Слушает порт `32777`, запускается в 2 репликах, доступ к подам открывается через Service типа ClusterIP и `kubectl port-forward`.

## Теоретические вопросы

### 1. Чем `git pull` отличается от `git fetch`

`git fetch` стягивает с удалённого репозитория новые коммиты, ветки и теги, но складывает их в локальные remote-tracking ссылки (`refs/remotes/origin/…`) и оставляет рабочую копию нетронутой. Я сам решаю, когда их слить с текущей веткой — `git merge` или `git rebase` вызываю вручную.

`git pull` делает то же самое и сразу же объединяет: внутри это `git fetch` + `git merge` (или `git rebase`, если настроено `pull.rebase`). Когда истории разошлись, придётся разбирать конфликты прямо здесь и сейчас, без возможности предварительно посмотреть, что прилетело.

Если коротко: `fetch` — «скачай, дай посмотреть», `pull` — «скачай и сразу объедини».

### 2. Soft link и hard link в Linux

Жёсткая ссылка (hard link) — это ещё одно имя, указывающее на тот же самый inode файла. На inode ведёт счётчик ссылок, и пока он больше нуля, данные физически живы.

Если удалить «оригинальное» имя файла, файл **останется доступным** через оставшиеся hard link'и — счётчик просто уменьшится на единицу.

Hard link **нельзя создать на директорию**: ядро запрещает это, чтобы не строить циклические зависимости в дереве файловой системы. Также жёсткая ссылка не跨сится через границы файловых систем — inode уникален только в пределах одного раздела.

Символическая ссылка (soft link / symlink) — это отдельный файл, внутри которого лежит путь к другому файлу или директории. Если удалить оригинал, symlink становится «висячим» и обращения по нему падают с `ENOENT`. На директории и через границы ФС — можно.

|                          | hard link          | soft link                |
| ------------------------ | ------------------- | ------------------------ |
| Что хранит               | ссылка на inode     | путь-строка              |
| После удаления оригинала | работает            | «висячий» указатель       |
| Через границы ФС         | нельзя              | можно                    |
| На директорию            | нельзя              | можно                    |
| Создать                  | `ln file link`      | `ln -s file link`        |

### 3. Как проверить сетевую доступность между двумя Linux-машинами

Сначала проверяю L3 — отвечает ли хост:

```bash
ping -c 4 192.168.1.10
```

Если пинга нет — это не значит, что хост мёртв. Часто ICMP режут фаерволом, а TCP-сервис при этом живёт. Поэтому проверяю порт:

```bash
nc -zv 192.168.1.10 32777
# либо
telnet 192.168.1.10 32777
# либо чистый bash, если есть /dev/tcp
timeout 2 bash -c 'cat < /dev/tcp/192.168.1.10/32777' && echo OK
```

Если надо понять, на каком хопе теряется пакет:

```bash
traceroute 192.168.1.10
mtr 192.168.1.10
```

Если адресуется по имени, проверяю DNS:

```bash
dig +short hello-app.default.svc.cluster.local
```

Если это веб-сервис — проверяю на уровне приложения:

```bash
curl -i http://192.168.1.10:32777/
```

Когда ничего не работает — смотрю локальный стек:

```bash
ip addr
ip route
ss -tlnp
ss -tn state established
```

Общий принцип — идти снизу вверх: link → route → port → application.

### 4. На каких компонентах Linux основана контейнеризация в Docker

Docker — это не виртуальная машина, а набор изоляций поверх механизмов ядра Linux:

1. **Namespaces** — изоляция различных сущностей:
   - `PID` — внутри контейнера своя нумерация процессов, главный PID равен 1;
   - `NET` — свой интерфейс, своя таблица маршрутов и iptables;
   - `MNT` — своё дерево mount-точек;
   - `UTS` — свой hostname;
   - `IPC` — своя очередь сообщений и семафоров;
   - `USER` — маппинг UID внутри контейнера на другие UID снаружи (root внутри = обычный пользователь снаружи).

2. **Cgroups (v1/v2)** — лимиты и учёт ресурсов: CPU, память, число процессов, ввод-вывод. Не дают одному контейнеру задушить всю машину.

3. **Capabilities** — гранулярные права root. Контейнер, запущенный от root, не имеет всех привилегий root'а хоста — только тот набор capabilities, который явно выдан.

Дополнительно:

- **OverlayFS / AUFS** — слоистая файловая система. Каждый слой Docker-образа — это diff файловой системы, а запись идёт в верхний слой через copy-on-write.
- **seccomp-bpf** — фильтрация системных вызовов, по умолчанию Docker блокирует ~44 небезопасных syscall'а.
- **AppArmor / SELinux** — мандатное управление доступом.

Получается, что Docker-контейнер — это просто процесс хоста, помещённый в набор namespaces и cgroups. Никакой виртуализации в привычном смысле нет.

### 5. Почему `COPY package.json` → `npm install` → `COPY . .` лучше, чем `COPY . .` → `npm install`

Дело в кешировании слоёв. Каждый `RUN`/`COPY` создаёт слой, и Docker пересоздаёт слой только если изменился его контекст (файлы в `COPY`) или сама команда.

Если писать так:

```dockerfile
COPY . .
RUN npm install
```

то любое изменение в любом файле проекта (даже в README) инвалидирует слой `COPY . .`, а за ним и `RUN npm install` — установка зависимостей запускается заново. На большом проекте это минуты на каждую сборку.

Если разделить:

```dockerfile
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
```

то:

- `COPY package.json` меняется только при правке манифеста зависимостей;
- `RUN npm ci` берётся из кеша, пока `package.json` и lock-файл не поменялись;
- `COPY . .` выполняется всегда, но это копирование, а не установка — быстро.

Итог — быстрая пересборка при правках кода и стабильные версии из lock-файла.

### 6. Могут ли два контейнера в одном поде слушать один и тот же порт

Нет. Все контейнеры в поде делят общий network namespace: у них один IP и одна таблица портов. Если оба попытаются забиндить `0.0.0.0:8080`, второй получит `EADDRINUSE`.

Поэтому контейнеры в одном поде обычно запускают на разных портах и общаются между собой через `localhost`. Это нормальный паттерн для основного приложения + sidecar (например, веб-сервер + адаптер метрик).

Если два приложения **обязаны** слушать один и тот же порт — их нужно разнести по разным подам, у каждого будет свой IP и свой network namespace.

### 7. Виды JOIN

JOIN соединяет строки из двух таблиц по условию. Основные варианты:

| JOIN                | Что возвращает                                                            |
| ------------------- | ------------------------------------------------------------------------- |
| `INNER JOIN`        | только строки, для которых нашлось совпадение в обеих таблицах             |
| `LEFT JOIN`         | все строки левой таблицы; при отсутствии совпадения справа — `NULL`       |
| `RIGHT JOIN`        | все строки правой таблицы; при отсутствии совпадения слева — `NULL`       |
| `FULL JOIN`         | все строки обеих таблиц; где совпадения нет — `NULL` с соответствующей стороны |
| `CROSS JOIN`        | декартово произведение: каждая строка левой × каждая строка правой        |
| `SELF JOIN`         | не отдельный синтаксис, а соединение таблицы с самой собой через алиасы   |

Пример `LEFT JOIN` — показать всех пользователей, включая тех, у кого нет заказов:

```sql
SELECT u.id, u.name, o.id AS order_id
FROM users u
LEFT JOIN orders o ON o.user_id = u.id;
```

### 8. `HAVING` vs `WHERE`

Оба условия фильтрации, но на разных стадиях запроса:

- `WHERE` фильтрует строки **до** группировки и агрегации. Не может использовать `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`.
- `HAVING` фильтрует результат **после** `GROUP BY` и агрегатов. Может их использовать.

Логический порядок выполнения SQL:

```
FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT
```

Пример:

```sql
SELECT department, COUNT(*) AS emp_count
FROM employees
WHERE status = 'active'      -- до агрегации
GROUP BY department
HAVING COUNT(*) > 5;          -- после агрегации
```

Правило выбора простое: условие на отдельную строку — `WHERE`; условие на результат агрегации — `HAVING`.

## Практическое задание

### Локальный запуск приложения

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
APP_PORT=32777 python app.py
```

Проверка:

```bash
curl http://localhost:32777/
```

### Сборка и публикация образа

```bash
docker login
docker build -t imeon/hello-app:1.0.0 .
docker run --rm -p 32777:32777 imeon/hello-app:1.0.0
docker push imeon/hello-app:1.0.0
docker tag imeon/hello-app:1.0.0 imeon/hello-app:latest
docker push imeon/hello-app:latest
```

### Установка Minikube

Установка — по официальной инструкции: <https://minikube.sigs.k8s.io/docs/start/>.

Запуск кластера:

```bash
minikube start
minikube status
kubectl cluster-info
kubectl get nodes
```

### Деплой в Minikube

```bash
kubectl apply -f k8s/deployment.yaml
kubectl apply -f k8s/service.yaml

kubectl get pods -l app=hello-app -o wide
kubectl get svc hello-app
kubectl describe deployment hello-app
```

### Проброс портов

```bash
kubectl port-forward svc/hello-app 8080:80
```

Открываем в браузере: <http://localhost:8080/>.

Несколько вызовов `curl http://localhost:8080/` покажут разные `hostname` — сервис балансирует между двумя репликами.

### Очистка

```bash
# Ctrl+C в окне port-forward
kubectl delete -f k8s/
minikube stop
```

## Архитектура

![Архитектура](docs/architecture.png)

Поток трафика:

1. Пользователь обращается на `localhost:8080`.
2. `kubectl port-forward` прокидывает трафик в `Service hello-app` (ClusterIP, порт 80).
3. kube-proxy через Endpoints балансирует запрос между двумя Pod'ами.
4. Каждый Pod слушает `32777` (targetPort сервиса).
5. gunicorn возвращает JSON с `hostname` пода — так видно, какая реплика ответила.
